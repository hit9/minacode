SPEC: @ mentions — file, mcp, skill
===================================
status   draft, awaiting three decisions (§10)
target   0.25.0
author   design pass on 2026-08-14, minacode 0.24.0


1. PROBLEM
----------
`@name` names an MCP server and `$name` a skill. Both are discoverable only if you
already know the symbol, and neither covers the thing a user points at most often: a
file in the project. There is no way to say "look at this file" without describing it
in prose and hoping the agent searches for the right thing.


2. GOALS / NON-GOALS
--------------------
G1  One prefix, `@`, opens a menu of everything mentionable: files, MCP servers and
    tools, skills.
G2  The menu appears on the keystroke that declares a mention and narrows as typing
    continues. (Already true as of 0.24.0; see §4.1.)
G3  File completion is fast enough to run synchronously in the prompt: p95 under 10ms
    on a 50k-file repository.
G4  A mentioned file reaches the model without a round trip, when its size allows.
G5  Nothing that works in 0.24.0 stops working.

N1  Not a file browser: no directory navigation UI, no preview pane.
N2  Not a retrieval system: no embedding, ranking by relevance, or content search.
    `@file:` completes paths, `Search` searches content.
N3  No new runtime dependency in phase 1 or 2. See §6.4 for where one is admissible.


3. SYNTAX
---------
    mention   := "@" kind ":" value | "@" server ("." tool)? | "$" skill
    kind      := "file" | "mcp" | "skill"
    value     := path | server ("." tool)? | skill
    path      := workspace-relative or absolute POSIX path, no spaces
    server    := [A-Za-z0-9_-]+
    tool      := [A-Za-z0-9_-]+
    skill     := [A-Za-z0-9_-]+

Namespaced forms are canonical and are what completion inserts:

    @file:minacode/tui.py       @mcp:github       @mcp:github.search      @skill:release

Legacy forms stay valid, undocumented-but-supported, resolved by the patterns that
already exist:

    @github     @github.search      $release

A mention ends at whitespace. A path containing a space cannot be mentioned; quote it
in prose and let the agent Read it. `@` preceded by a word character is not a mention
(protects email addresses); `$` keeps its existing negative lookbehind.


4. COMPLETION
-------------
4.1 Trigger (implemented in 0.24.0, cadd968)
    Buffer.complete_while_typing stays False. TuiApp._offer_mention_completions starts
    completion when the text before the cursor matches MENTION_RE. prompt_toolkit clears
    complete_state on each insert and the hook reopens it, so the menu narrows live.
    Verified: "@gi" -> [github, gitlab], then "th" -> [github].

4.2 Menu content
    query empty      the three kinds, as rows: "file:", "mcp:", "skill:", each with a
                     one-line meta ("files in this repo", "MCP servers and tools",
                     "installed skills")
    query non-empty  merged matches from all three sources, kind shown in display_meta,
                     kinds themselves still offered while they prefix-match
    after "@file:"   paths only
    after "@mcp:"    servers, then "server." expands to that server's tools
    after "@skill:"  skill names

4.3 Matching and ranking
    Today every completion in this codebase is strict prefix:
        CommandCompleter.matches -> value.startswith(prefix)
    That is right for short known symbols and wrong for paths: nobody types
    "minacode/cli/" to reach view.py.

    M1  Case-insensitive throughout. The path cache stores a lowercase copy so no
        keystroke pays for .lower().
    M2  Servers, skills, tools, kinds: prefix match, then substring. These vocabularies
        are tens of items; prefix keeps them predictable.
    M3  Files: substring over the whole workspace-relative path. "view" finds
        minacode/cli/view.py; "cli/view" finds it too.
    M4  Subsequence ("cliview" -> minacode/cli/view.py) is NOT in phase 2. See §6.4:
        it costs more than the frame budget in pure Python.
    R1  Rank: prefix of basename, then substring of basename, then substring of path.
    R2  A query containing "/" or "." ranks files first; a bare word ranks servers and
        skills first.
    R3  Ties: shorter path first, then alphabetical. Deterministic — no MRU, no
        recency, nothing that makes the same query answer differently twice.
    R4  Cap at 50 rows.

4.4 Insertion
    Selecting a kind inserts "kind:" and leaves the menu open on that kind's source.
    Selecting a value inserts the whole canonical mention. Completion.start_position
    replaces from the "@".


5. RESOLUTION
-------------
Mentions resolve per turn, from the text of that turn's user message, into extra user
messages appended after it — the mechanism engine.py already uses for MCP and skills.
The user's own text is never rewritten.

5.1 New: FILE MENTIONS block

    --- FILE MENTIONS ---
    The user explicitly referenced these files. Treat them as the subject of the request.

    [minacode/tui.py] 1619 lines, 68 KB — too large to inline; Read the part you need
    [minacode/hints.py] 92 lines
    <file contents>

5.2 Inlining rule (DECISION D1, §10)
    inline    file is inside the workspace AND <= 400 lines AND <= 64 KB
    pointer   otherwise: path, line count, size, and the instruction to Read
    Cap: 10 files per turn; further mentions become pointers with a note.
    A missing or unreadable path is reported as "[path] not found" — never silently
    dropped, since the user meant something by it.

5.3 Outside the workspace
    Never inlined, whatever the size. The agent reaches it through Read, which keeps
    the out-of-workspace confirmation in safety.md on the path.

5.4 mcp / skill
    Unchanged behavior. The prefixed forms feed the existing resolvers.


6. FILE SOURCE
--------------
6.1 Candidates
    git repo:      `git ls-files` + `git ls-files -o --exclude-standard` (tracked plus
                   untracked-not-ignored)
    non-git:       the gitignore-aware walk SearchTool.files already implements,
                   bounded to 50k entries
    Both are relative to session.cwd.

6.2 Caching
    One list per session, built on first use. Rebuilt when older than 5s at the moment
    a completion starts — never on a timer, never in the background: a stale entry
    costs one wrong row, a background thread costs a race with the event loop.

6.3 Measured (2026-08-14; synthetic 50k-path list, this machine)
    git ls-files, this repo         132 paths    1.9ms
    git ls-files -o --exclude-std     0 paths    7.5ms
    substring over 50k paths                     0.8 - 1.3ms      <- inside G3
    subsequence over 50k paths                  14.7 - 26.8ms     <- over G3
    subsequence over 50k basenames              10.9 - 15.1ms     <- over G3
    char-set gate then subsequence              13.3ms            <- over G3
    Substring is the only matcher that fits the budget in pure Python. This is why M4
    holds phase 2 to substring: fuzzy matching is a dependency decision, not a
    free upgrade.

6.4 When a dependency is admissible
    Fuzzy file matching, in phase 3, behind the same completion API. rapidfuzz does
    this work in C++ and answers 50k candidates in well under a millisecond, which is
    the gap the numbers above describe. Adopt it only if substring proves annoying in
    daily use — "cliview" is a nice trick, "view" is what people actually type.


7. SURFACE CHANGES
------------------
    minacode/mentions.py        new: FileMentions (source + resolver)
    minacode/cli/view.py        CommandCompleter: kind dispatch, merged menu, ranking
    minacode/engine.py          one more resolver call in the turn assembly
    minacode/mcp.py             MENTION_PATTERN accepts the optional "mcp:" prefix
    minacode/skill.py           MENTION_PATTERN accepts "@skill:" beside "$"
    minacode/session/__init__.py  holds the cached path list
    minacode/hints.py           a hint naming @file:
    docs/usage.md               Mentions section rewritten for three kinds
    docs/tools.md               note that @file: is not a substitute for Read/Search

No change to: the request protocol, the session snapshot, the tool registry, or any
provider path. A mention is a turn-local input transform.


8. PHASES
---------
P1  Namespaced syntax and the merged menu over today's two sources.
    done when: @mcp: and @skill: complete and resolve; bare @server and $skill still
    work; the menu shows kinds on "@" and merged matches as you type.
P2  @file: completion and the FILE MENTIONS resolver.
    done when: completing a path inserts @file:<path>; small files inline; large and
    outside-workspace ones become pointers; missing paths report themselves.
P3  Fuzzy file matching behind rapidfuzz, only if P2's substring matching proves
    annoying in daily use (§6.4).


9. TESTS
--------
T1  grammar: each canonical form parses; legacy forms parse; an email address and a
    price like "$30" do not.
T2  completion: "@" lists three kinds; "@fi" keeps "file:"; "@file:tu" lists paths;
    "@mcp:git" lists servers; "@mcp:github." lists that server's tools; the list
    narrows as characters arrive (extend the 0.24.0 harness test).
T3  matching: case-insensitive; "view" finds minacode/cli/view.py and "cli/view"
    finds it too; a "/"-bearing query puts files first; deterministic order for equal
    scores; 50-row cap.
T4  source: git and non-git roots both produce paths; the cache refreshes after its
    window; an untracked new file appears.
T5  resolver: small file inlines; large file becomes a pointer with its size; an
    outside-workspace path is never inlined; a missing path is reported; the 10-file
    cap holds.
T6  turn: the block lands as its own user message and the user's text is unchanged.
T7  performance: filtering a synthetic 50k-path list stays under 10ms (guards G3
    against an accidental O(n^2)).


10. DECISIONS PENDING
---------------------
D1  @file: semantics — bounded inline (§5.2, recommended) or pointer-only.
D2  Menu shape — merged with kind labels (§4.2, recommended) or strict two-level:
    "@" offers only kinds, values come after a kind is chosen.
D3  $skill — keep indefinitely as an alias (recommended, costs one regex) or document
    @skill: and let $ fade.

Answers change §4.2, §5.2 and §7 only; the rest of the spec holds either way.
