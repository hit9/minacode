FZF-STYLE FILE COMPLETION SPECIFICATION
=======================================

Status: Proposed
Scope: File mention discovery, selection, parsing, and expansion
Supersedes: The file-completion and file-mention portions of SPEC-at-mentions.txt
Does not supersede: Skill or MCP completion behavior outside namespace parsing


1. Objective
------------

Keep file completion, but replace the current prefix/substring-style file menu with an
fzf-like picker whose interaction and performance remain useful in repositories containing
hundreds of thousands of files.

The feature must:

1. use the real fzf executable for fuzzy interaction when it is available and passes the
   required capability and performance gates;
2. never run a Python fuzzy matcher over the full repository on each keystroke;
3. keep a non-fuzzy file-completion fallback when fzf is unavailable or unsupported;
4. never block prompt-toolkit's input loop while discovering or filtering files;
5. exclude every `.git` directory and every path matched by applicable Git ignore rules;
6. correctly represent spaces, Unicode, punctuation, tabs, and newlines in file names;
7. resolve file mentions on every user-message path, including messages queued while the
   agent is running.

This is not a proposal to abandon file completion. Fuzzy matching is conditional on a fast
fzf backend; file completion itself is not conditional on fzf.


2. Decisions
------------

The following are settled decisions for this implementation:

* The fuzzy backend is the external `fzf` executable, used as one long-lived interactive
  process per picker session. It is not invoked once per keystroke and is not used through
  repeated `fzf --filter` calls.
* Opening the picker is explicit: press Tab while the cursor is inside an unfinished
  `@file:` mention. Merely typing `@file:` does not take over the terminal.
* fzf receives the existing text after `@file:` as its initial query and owns subsequent
  fuzzy matching, input handling, result rendering, and selection for that picker session.
* RapidFuzz is not added. It is a fast compiled matcher, but it would still leave Python in
  charge of candidate materialization, per-query orchestration, result allocation, and UI
  integration. It also would not reproduce fzf's ranking and interaction closely enough to
  justify a second fuzzy implementation.
* prompt-toolkit's fuzzy completer is not used for repository paths.
* There is no pure-Python fuzzy fallback. If real fzf is unavailable, too old, incompatible,
  or fails the performance gate, completion falls back to asynchronous literal substring
  matching.
* fzf is optional and is never downloaded, installed, or upgraded automatically.
* Actual file rows are not inserted into the generic bare-`@` menu. The bare menu advertises
  the `@file:` namespace; file discovery begins only when the file picker is requested.
* File names requiring quoting use a JSON string after `@file:`. Regex-only parsing is
  replaced by a scanner.
* Ignore behavior follows Git semantics, including nested `.gitignore` files, negation rules,
  `.git/info/exclude`, and the user's global Git excludes where Git supplies the candidate
  list. A tracked file that currently matches an ignore rule is also excluded, per the
  product requirement in this specification.


3. Review Findings Addressed
----------------------------

The current branch has the following substantive gaps. This specification treats them as
release blockers for the new file picker, not as optional follow-up work.

3.1 Matching and UI performance

* `minacode/cli/view.py::_matching_files` linearly scans the complete candidate tuple and
  allocates every match before the UI truncates the displayed rows.
* Local measurements of the current literal matcher were approximately 7 ms at 50,000
  candidates, 16 ms at 100,000, and 80 ms at 500,000. These measurements exclude candidate
  discovery and fuzzy scoring.
* `complete_input` synchronously materializes completions on the prompt-toolkit path.
* `FileMentions.paths()` may synchronously refresh its cache and wait for a Git subprocess.
* The non-Git `MAX_CANDIDATES` limit is ineffective because `SearchTool.files()` finishes a
  full traversal and returns a list before the caller applies the limit.

3.2 Incorrect path discovery

* Git output is decoded as newline-delimited text. Git can quote non-ASCII names, and newline
  is itself legal in a POSIX file name.
* The Git source includes tracked files even when they later match an ignore rule.
* The Python fallback reads only the root `.gitignore` and does not implement nested ignore
  files or negation rules.
* `.git` is skipped by current implementations, but this is an incidental property rather
  than an explicit invariant shared by every source.

3.3 Incorrect mention grammar and resolution

* File completion and file resolution accept different character sets. Spaces and many
  Unicode or punctuation-heavy names can appear as candidates but cannot be selected or
  parsed reliably.
* Independent file, MCP, and skill regular expressions permit namespace collisions such as
  interpreting `@file:a.py` as an MCP server mention. Email-like text can also be matched.
* Messages queued while the agent is running bypass file-mention expansion.
* Mention deduplication uses the spelling of a path instead of canonical file identity.
* File inspection can miscount an unterminated one-line file as zero lines, and some `stat`
  or open errors can abort a turn instead of degrading to a pointer/error entry.
* Small binary files are not explicitly distinguished from text files before inlining.

3.4 Incomplete controls and tests

* The 50-row display cap applies to file/merged menus but not consistently to explicit skill
  and MCP menus.
* The existing timing test measures a single warm call over in-memory candidates. It does
  not cover discovery, 100,000/500,000 candidates, cold state, p95 latency, match-heavy
  queries, or interactive fzf behavior.
* `MAX_CANDIDATES` is operationally dead as a traversal guard even though the symbol is
  referenced. It must be removed or moved into a streaming producer where it can take effect.


4. User Experience
------------------

4.1 Entry points

The generic inline menu continues to handle namespaces, skills, and MCP entries. For file
completion it behaves as follows:

* Typing `@` may show `@file:`, `@mcp:`, and `@skill:` namespace rows, plus bounded MCP/skill
  matches. It does not enumerate repository files.
* Selecting the file namespace inserts exactly `@file:` and leaves the cursor after the
  colon.
* Pressing Tab while the cursor is in `@file:<query>` opens the file picker.
* Pressing Tab elsewhere retains the existing quick-hint/completion behavior.
* Pasting or manually typing a complete `@file:` mention remains supported; the picker is
  an aid, not a required input path.

The explicit Tab trigger is important. It avoids surprising terminal takeover during paste,
history navigation, editing, or programmatic buffer updates.

4.2 Picker session

When fzf is available:

1. Capture the complete input buffer, cursor position, and the active mention span.
2. Suspend prompt-toolkit with the existing `run_in_terminal(..., in_executor=True)` pattern.
3. Start one fzf process and stream candidates to its stdin once.
4. Seed fzf with the current text after `@file:` using `--query`.
5. Let fzf own all keys until Enter, Escape, EOF, or failure.
6. On Enter, replace only the captured mention span with the encoded selected path. Preserve
   all text before and after the span and place the cursor after the replacement.
7. On Escape, no match, or EOF, restore the original buffer unchanged.
8. Restore prompt-toolkit and redraw even when the child process fails.

The picker has no preview pane, file icons, content reads, syntax highlighting, or metadata
columns. The only candidate payload is the workspace-relative path. This keeps startup and
rendering costs predictable.

4.3 Non-fzf fallback

When fzf is unavailable or unsupported, Tab still performs file completion:

* Candidate discovery and filtering run outside the prompt-toolkit input thread.
* Matching is case-insensitive literal substring matching over normalized display paths.
* At most 50 matches are returned to the inline menu.
* Each request carries a monotonically increasing generation/query identifier. Results are
  installed only if the buffer, cursor, and candidate generation still match; stale results
  are discarded.
* Cancellation or a newer query stops presenting older work. Implementations may allow an
  already-running discovery subprocess to finish, but its results must not overwrite newer
  state.
* The fallback may be slower to produce results in a very large repository, but it must not
  freeze typing or rendering.

No fallback path may silently switch to full-repository Python fuzzy scoring.


5. Mention Grammar
------------------

5.1 Canonical forms

A selected path is stored in one of two forms:

    @file:src/minacode/tui.py
    @file:"docs/design notes/中文.txt"

Use the bare form only when the path contains no whitespace, quote, backslash, ASCII control
character, or character that would make the token boundary ambiguous. Otherwise use a JSON
string produced with `json.dumps(path, ensure_ascii=False)`.

Examples:

    path                         canonical mention
    ---------------------------  ----------------------------------------
    src/app.py                   @file:src/app.py
    docs/design notes.txt        @file:"docs/design notes.txt"
    文档/设计.txt                 @file:"文档/设计.txt"
    odd\tname.txt                @file:"odd\tname.txt"
    odd\nname.txt                @file:"odd\nname.txt"

NUL does not need an encoding because it is not legal in a POSIX path component.

5.2 Scanner contract

Introduce one scanner for all `@` namespaces instead of independent overlapping regular
expressions. It returns typed spans with start, end, kind, decoded payload, and original text.

The scanner must enforce:

* `@file:`, `@mcp:`, and `@skill:` are reserved namespaces.
* Legacy `@server` MCP mentions are accepted only when no reserved namespace prefix is
  present.
* A mention cannot begin in the middle of an email or identifier. `a@b.com` is plain text.
* JSON-string payloads are decoded with a real JSON decoder, including escaped quote,
  backslash, tab, newline, and Unicode sequences.
* Invalid or unterminated quoted payloads remain editable completion spans but are not
  expanded as resolved mentions.
* A bare file payload ends at whitespace. Its punctuation is not stripped because the
  punctuation may be part of the file name.

Completion, buffer replacement, MCP collection, and engine-side expansion must all consume
the scanner's spans. There must be no second grammar embedded in view-layer regexes.


6. Candidate Discovery
----------------------

6.1 Common invariants

Every candidate producer must return workspace-relative paths and enforce all of these rules:

* exclude any path having a component exactly equal to `.git`;
* exclude files matched by applicable Git ignore rules;
* include hidden files that are not ignored;
* include only existing regular files at the time they are emitted;
* never follow directory symlinks during discovery;
* use NUL-delimited transport between subprocesses and Python;
* preserve Unicode and arbitrary non-NUL bytes supported by the runtime's filesystem codec;
* normalize separators to `/` for display and mention serialization;
* deduplicate by normalized workspace-relative identity without applying unconditional
  case-folding on case-sensitive filesystems;
* produce candidates incrementally instead of first constructing a second complete list.

Candidate discovery must not read file contents.

6.2 Git workspace source

When the workspace is inside a Git worktree, Git is authoritative for ignore semantics.
Resolve the repository top level once and scope every pathspec to the configured workspace.

Build the included stream from the NUL-delimited equivalent of:

    git ls-files -z --cached --others --exclude-standard -- <workspace-pathspec>

Build the tracked-but-ignored exclusion set from the NUL-delimited equivalent of:

    git ls-files -z --cached --ignored --exclude-standard -- <workspace-pathspec>

Subtract the second set from the first stream. This extra subtraction is intentional: normal
Git commands continue to report tracked files even if a later ignore rule matches them, while
this product explicitly requires all ignored paths to be absent.

The implementation must use argv arrays, never a shell string. It must handle a workspace
equal to the repository root and a workspace located in a subdirectory. It must not expose
files outside the workspace.

`.git/info/exclude` and configured global excludes are included through `--exclude-standard`.
An explicit `.git` component check remains mandatory as a defense-in-depth invariant.

6.3 Non-Git workspace source

When no Git worktree is available, prefer ripgrep because it is the only accepted fast
third-party discovery backend for this phase:

    rg --files --hidden --no-require-git --glob !**/.git/** --null

The exact argv must be validated against the installed ripgrep's help/capabilities; equivalent
flag spellings are allowed. `--no-require-git` is required so nested `.gitignore` files are
respected even outside a Git repository. The explicit negative `.git` glob is required because
`--hidden` would otherwise expose it.

If ripgrep is absent or incompatible, use a background Python walker solely as a correctness
fallback. It must implement nested Git ignore and negation semantics through a direct,
well-maintained gitignore parser dependency; it must not grow a new ad-hoc partial parser.
That dependency is for ignore correctness, not fuzzy ranking. The fallback remains
nonblocking and may stream results progressively.

If no correct ignore implementation is available, do not show candidates from a traversal
that might leak ignored paths. Return an actionable `file discovery unavailable` state for
that workspace. Do not weaken the ignore invariant to preserve partial completion.

6.4 Cache and invalidation

Candidate state is runtime-only and is never persisted in session snapshots.

Maintain one immutable candidate snapshot per workspace plus a generation number. A picker
may stream a cold source immediately; subsequent sessions may reuse the completed snapshot.

Invalidate lazily when any of these change:

* Git index metadata;
* any relevant `.gitignore` or `.git/info/exclude` file observed by the source;
* configured global exclude metadata when its location is known;
* workspace root;
* a conservative time-to-live for ordinary file creation/deletion.

Invalidation must only mark the snapshot stale on the UI thread. Refresh happens in a worker
or while fzf is active. A refresh failure leaves the last successful snapshot usable only if
its paths are revalidated before insertion; otherwise report discovery unavailable.


7. fzf Process Contract
-----------------------

7.1 Capability selection

Resolve fzf lazily with `shutil.which("fzf")`. Cache capability success/failure for the
process lifetime. Do not add startup-time subprocesses to normal minacode launch.

The implementation requires support for:

* NUL-delimited input;
* NUL-delimited output;
* path scoring scheme;
* initial query;
* single selection;
* height or otherwise safely restorable terminal rendering.

Prefer a small behavioral probe or option-compatible invocation over parsing version strings.
An unsupported-option exit marks fzf unavailable and routes future sessions to the fallback.

7.2 Invocation

The baseline invocation is equivalent to:

    fzf
      --read0
      --print0
      --scheme=path
      --no-multi
      --no-multi-line
      --layout=reverse
      --height=~60%
      --border
      --prompt=files>
      --query <current-query>

Option spellings may vary by supported fzf version, but behavior must not. There is no preview
command and no shell evaluation.

Write each workspace-relative candidate followed by NUL to stdin. Read exactly one
NUL-terminated selection from stdout. Bound stderr capture so a malfunctioning child cannot
consume unbounded memory.

Interpret exit status as follows:

* 0: selection; validate it is an emitted candidate and still resolves inside the workspace;
* 1: no match; leave the buffer unchanged;
* 130: user cancellation; leave the buffer unchanged;
* any other code: restore the UI, mark this fzf capability failed, and use the fallback on
  the next request. A concise transient hint may show the failure.

If candidate production fails while fzf is running, close stdin, allow the user to cancel or
select already-emitted candidates, and revalidate any selection.

7.3 Environment isolation

User fzf defaults can inject commands, previews, transforms, incompatible output modes, or
different delimiters. Start the child with a copied environment in which these variables are
removed:

* `FZF_DEFAULT_COMMAND`
* `FZF_DEFAULT_OPTS`
* `FZF_DEFAULT_OPTS_FILE`

Do not accept arbitrary fzf option strings in this phase. Color-related environment may pass
through only when it cannot change the input/output protocol.


8. File Mention Expansion
-------------------------

8.1 Shared message boundary

Add one engine-owned expansion function and call it for every accepted user message before
provider context is composed. This includes:

* the initial prompt;
* ordinary follow-up prompts;
* messages queued while the agent is running;
* messages accepted immediately after a tool call or pending-input drain.

TUI selection only edits text. It does not perform semantic expansion. This keeps behavior
identical for interactive, queued, pasted, and non-TUI inputs.

8.2 Resolution and safety

For each decoded file payload:

1. Resolve it relative to the workspace unless it is absolute.
2. Normalize it and resolve symlinks for the containment check.
3. Reject it if the resolved target is outside the workspace.
4. Reject directories and non-regular files.
5. Catch races and all expected `stat`, resolve, and open errors per mention. One bad mention
   must not abort the whole turn.
6. Deduplicate aliases (`a.py`, `./a.py`, an equivalent absolute path, or symlink aliases)
   by canonical target identity.
7. Revalidate immediately before reading or creating a pointer block.

Selection from fzf is not trusted merely because it was emitted earlier.

8.3 Inline versus pointer content

Retain the existing overall file-context policy, with these corrections:

* Detect binary content before inline decoding. Binary files are represented as metadata
  pointers and are never blindly injected as text.
* Count a final unterminated line correctly. A non-empty one-line file reports one line.
* Catch size, line-count, encoding, and open failures and report them in the individual file
  entry.
* Cap inline file bodies at 10 per user message. Additional valid mentions become pointer
  entries.
* Cap total expanded file entries at 50 per user message and report the number omitted.
* Preserve the existing per-file and aggregate byte/token budgets; make the budgets explicit
  constants covered by boundary tests.


9. Module Ownership
-------------------

Use these ownership boundaries; exact private class names may follow local naming conventions.

`minacode/mentions.py`
    Owns the unified mention scanner, file mention encoding/decoding, candidate-source
    interface, Git/ripgrep/Python producers, immutable candidate snapshots, fzf process
    adapter, and file resolution/expansion. It must not import prompt-toolkit.

`minacode/cli/view.py`
    Owns only bounded inline completion presentation. It may advertise `@file:` and render
    fallback rows supplied asynchronously. It must not scan the filesystem, run Git, invoke
    fzf, or perform full-repository ranking.

`minacode/tui.py`
    Detects Tab in an active file mention, snapshots the buffer/span, suspends the terminal
    through `run_in_terminal`, invokes the picker adapter, and atomically applies a validated
    result. It owns redraw and buffer restoration.

`minacode/engine.py`
    Calls the shared semantic mention-expansion boundary for every accepted user message,
    including pending inputs.

`minacode/session/`
    Stores no candidate list, subprocess, cache timestamp, or capability result in durable
    snapshots. Runtime-only state may be attached through the existing non-semantic runtime
    ownership pattern if necessary.

Avoid pass-through wrappers. If the existing file-mention module already provides the nearest
ownership pattern, extend it rather than creating parallel abstractions with identical roles.


10. Concurrency and Failure Rules
---------------------------------

* The prompt-toolkit thread performs only span detection, state capture, generation checks,
  and final buffer replacement.
* Git, ripgrep, Python traversal, candidate filtering, and fzf waiting run outside the input
  thread.
* Only one picker may own the terminal at a time. A second Tab while a picker is active is
  ignored.
* Cancellation is idempotent. It must not leave a child process, producer thread, pipe, or
  terminal mode behind.
* Producer writes must handle a consumer that exits early without surfacing broken-pipe noise
  to the user.
* Application shutdown terminates an active fzf child, closes pipes, and joins bounded worker
  cleanup without hanging exit.
* Late fallback results must never mutate a buffer whose text or cursor has changed.
* File creation/deletion races are normal. They produce a stale-selection/no-longer-exists
  result, not a crash.


11. Performance Contract
------------------------

11.1 Supported corpus

Benchmark at least 50,000, 100,000, and 500,000 candidate paths. Include both a deterministic
synthetic corpus and at least one real large-repository corpus. Queries must include:

* empty query;
* no match;
* highly selective basename;
* directory plus basename fragments;
* match-heavy short query;
* Unicode query;
* long/deep path query.

11.2 Release gates

The feature is acceptable only when all of these are true on the documented reference
machine after warmup:

* no prompt-toolkit callback attributable to file completion blocks for more than 16 ms;
* fzf interactive query-to-render p95 is below 10 ms at 50,000 candidates;
* fzf interactive query-to-render p95 is below 30 ms at 500,000 candidates;
* no measured hot query at 500,000 candidates exceeds 50 ms;
* opening a cold picker restores a responsive terminal immediately; candidate discovery may
  continue streaming and is measured separately;
* steady-state candidate storage is one canonical snapshot plus backend storage, not a new
  all-match Python list for every query;
* cancellation and selection do not leave measurable child-process or file-descriptor growth
  across 100 repeated sessions.

The p95 numbers must come from repeated samples, not one timing assertion. Normal unit tests
must not fail on scheduler jitter; performance gates run in a dedicated benchmark job or
documented local benchmark command.

If real fzf fails these gates, do not ship the fuzzy picker as default. Keep asynchronous
literal file completion and report the benchmark evidence. Do not substitute RapidFuzz or a
Python fuzzy loop without a new design review and equivalent end-to-end measurements.

11.3 Discovery metrics

Measure Git, ripgrep, and Python-fallback discovery independently for cold and warm state:

* time to first emitted candidate;
* time to complete enumeration;
* peak resident memory attributable to candidate state;
* candidate count before and after ignore filtering;
* cancellation latency.

Discovery time is not included in fzf query latency, but it must never run synchronously on
the input path.


12. Verification Matrix
-----------------------

12.1 Scanner and serialization unit tests

Cover bare and quoted paths, spaces, tabs, newlines, escaped quotes, backslashes, Unicode,
leading dash, colon, hash, at-sign, invalid JSON, unterminated JSON, punctuation boundaries,
email addresses, reserved namespaces, and legacy MCP mentions. Assert round-trip encoding and
exact source spans.

12.2 Candidate-source contract tests

Run the same black-box candidate contract against each available source. Fixtures must cover:

* tracked and untracked files;
* root and nested `.gitignore` files;
* ignore negation;
* ignored directories;
* `.git/info/exclude` and global excludes for the Git source;
* a tracked file that later becomes ignored;
* `.git` at the root and nested `.git` directories;
* hidden but non-ignored files;
* spaces, Unicode, tabs, and newlines in names;
* workspace as repository root and workspace as a subdirectory;
* symlinked directories and files;
* deletion during enumeration.

Assert byte-safe/NUL-safe behavior; do not infer correctness by comparing newline-split output.

12.3 fzf adapter tests

Use a fake executable to assert argv, isolated environment, NUL input, NUL output, initial
query, validation of unknown output, bounded stderr, and exit handling for 0, 1, 130, and
unexpected statuses. Cover broken pipes, producer failure, child hang timeout/termination, and
application shutdown. These deterministic tests must not require a developer's real fzf.

Add a separate optional integration/benchmark test for the real supported fzf executable.

12.4 TUI tests

Use the existing TUI harness plus a PTY-level integration where needed. Cover:

* Tab opens the picker only inside an active `@file:` span;
* the current query is seeded correctly;
* selection replaces only that span in a multi-mention/multi-line buffer;
* Escape and no-match preserve text and cursor;
* terminal rendering is restored after success, cancellation, and failure;
* repeated Tab cannot create overlapping pickers;
* stale asynchronous fallback results are discarded;
* both chat and running/queued states accept and later expand file mentions.

12.5 Resolver tests

Cover canonical alias deduplication, absolute and relative paths, symlinks inside/outside the
workspace, missing/unreadable/raced files, directories, special files, binary files, empty
files, one-line files without a final newline, invalid encodings, per-file/aggregate limits,
the 10-inline cap, and the 50-entry cap.

12.6 Full validation before completion

After implementation, run targeted tests while iterating, then:

    uv run pytest
    uv run ruff check minacode
    uv run ruff format --check minacode
    uv run pyright

User-visible behavior requires an Unreleased changelog entry. If user-facing documentation is
updated, follow the repository's English-source, Chinese-locale, catalog, and dual-build
workflow.


13. Delivery Plan
-----------------

Phase 1: Correctness boundary

* Introduce the unified scanner and canonical file-mention encoding.
* Correct Git/non-Git candidate discovery, NUL transport, ignore behavior, and `.git`
  exclusion.
* Move file discovery/ranking off the synchronous view path.
* Expand mentions through the shared boundary for initial and queued messages.
* Fix canonical deduplication, line counts, binary handling, and per-file error isolation.

Exit criterion: literal fallback completion and direct mention expansion are correct without
fzf, including all ignore and filename edge cases.

Phase 2: Real fzf picker

* Add lazy capability detection and isolated process invocation.
* Integrate prompt-toolkit suspension/restoration and atomic span replacement.
* Stream cold candidates and reuse immutable warm snapshots.
* Add deterministic fake-fzf and PTY coverage.

Exit criterion: fzf selection is functionally complete, cancellation-safe, and never required
for baseline file completion.

Phase 3: Performance qualification and cleanup

* Add the dedicated benchmark corpus and report p50/p95/max values.
* Enable fzf by default only if all release gates pass.
* Remove `_matching_files` from the hot path and remove or relocate the ineffective
  `MAX_CANDIDATES` guard.
* Remove obsolete file-completion regexes and cache paths after call-site verification.
* Update changelog and user documentation, including optional fzf installation guidance and
  fallback behavior.

Exit criterion: correctness suite, full repository validation, resource-leak checks, and
performance gates all pass.


14. Non-goals
-------------

This phase does not add:

* file content search;
* a preview pane;
* directory selection;
* multi-select;
* icons or Git-status columns;
* MRU/frecency ranking;
* configurable arbitrary fzf commands/options;
* bundled or automatically installed fzf/ripgrep binaries;
* a RapidFuzz or prompt-toolkit fuzzy backend;
* file watching as a correctness requirement;
* persistence of repository candidate lists in session snapshots.


15. Acceptance Checklist
------------------------

The work is complete only when every statement below is true:

[ ] File completion still works when fzf is absent.
[ ] Real fzf supplies the fuzzy experience when supported; no per-keystroke child process is
    created.
[ ] Typing remains responsive during cold discovery and match-heavy queries in a 500,000-file
    corpus.
[ ] `.git` never appears from any producer.
[ ] Every applicable ignored path is absent, including tracked-but-now-ignored files.
[ ] Spaces, Unicode, tabs, and newline-containing file names round-trip through discovery,
    selection, mention text, parsing, and resolution.
[ ] Email text and reserved file/skill namespaces cannot be consumed as legacy MCP mentions.
[ ] Initial and queued user messages use the same mention-expansion boundary.
[ ] Cancellation/failure restores the buffer and terminal and leaves no child/resource leak.
[ ] Resolver races and per-file I/O errors cannot abort the entire turn.
[ ] The complete verification matrix and repository quality commands pass.
[ ] The recorded p95/max benchmark results meet the release gates before fuzzy mode is enabled
    by default.
